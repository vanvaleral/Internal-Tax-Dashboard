# UI REQUIREMENTS

## Current UI Assessment

The current UI should be preserved as a valuable starting point.

It already demonstrates:
- strong operational density
- workspace-based separation
- good role-oriented information architecture
- compact recurring control behavior
- useful note interactions
- a practical client-centric lens

The major issue is not that the UI is bad.
The major issue is that the current UI is mostly implemented in a large standalone demo file.

## UI Principles to Preserve

- workspace-based navigation
- compact operational scanning
- recurring compliance as a dense matrix
- cases separate from recurring work
- annual controls separate from monthly controls
- management focused on exceptions and oversight
- notes as compact lightweight interactions
- search/filter/sort support

## Recurring Monthly Compliance UI

Should continue to emphasize:
- one client = one row
- grouped obligation visibility
- inline operational updates
- obvious blockers and deadlines
- completed history separated from active queue

## Annual Compliance UI

Should continue to use control-sheet behavior rather than oversized workflow cards.

### Annual Accounting
- compressed progression column
- compact dates and notes
- per-PIC progress visibility

### Annual Tax
- milestone/checklist visibility with fast scanning

## Cases UI

Should remain distinct from recurring compliance.

Kanban is acceptable here because cases have more project-like progression.

## Clients UI

Should preserve:
- active clients
- proposals
- contract monitoring
- fee analytics placeholder

## Management UI

Should remain an exception/oversight workspace, not an operational editing page.

## UI Requirements for Future Evolution

- keep visual consistency with the current design language
- migrate incrementally from `public/demo.html` to reusable React modules
- do not redesign without operational reason
- preserve scanning speed over decorative complexity

## Accessibility / Usability Notes

- keyboard efficiency should improve over time
- form-heavy repeated actions should be minimized
- visual status semantics should remain obvious and consistent
